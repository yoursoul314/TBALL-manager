# TB Manager 개발 명세 v0.1

## 1. 목적과 범위

중학교 티볼 수업에서 iPad·PC로 경기를 기록하고 선수별 타격·수비·주루·팀워크 근거를 모읍니다. 기능평가와 실전 기록을 바탕으로 최종 엔트리 및 최적 포지션을 추천하는 것이 목표입니다.

이번 단계는 실행 가능한 기본 화면, 확정 규칙 엔진, 원본 이벤트 기반 재계산, 초기 모델, 자동 테스트와 배포 기반입니다. 미확정 평가 알고리즘을 확정된 것처럼 자동 적용하지 않습니다.

## 2. 계층과 의존 방향

```text
React components
    ↓ commands / queries
domain model + config
    ↓
engine (replayGame) → statistics (calculateStats)
                    → evaluation (positionScore, recommendPositions)
    ↓
WorkspaceRepository → LocalWorkspaceRepository
                    → [TODO] IndexedDB/outbox + authenticated SyncPort
```

- 경기 엔진은 React·DOM·localStorage에 의존하지 않는 순수 TypeScript 함수입니다.
- 통계는 저장된 합계에서 증분 수정하지 않고, 원본 이벤트와 정책으로 재계산합니다.
- 평가 함수는 경기 판정과 독립적입니다. 정책 변경이 경기 원본이나 승패 규칙을 변경하지 않습니다.
- Zod는 데이터 접근 경계에서 버전·범위·참조·경기 재생을 검증합니다.
- 원본 이벤트는 추가만 하며, 직전 이벤트 정정은 RETRACT 이벤트로 남깁니다.

## 4. 초기 모델

- Player: 안정 ID, 팀 ID, 표시 이름, 등번호, 활성 여부. 이름을 식별자로 쓰지 않습니다.
- Team: ID, 이름, 색상.
- Game: ID, 이름, 생성 시각, 이닝, rulesVersion, 양 팀 ID, 명단 스냅샷, 타순 슬롯 배열.
- GameEvent: schemaVersion=1, UUID, gameId, 경기별 연속 sequence, 기록 세션 deviceId, ISO UTC recordedAt, 타입별 payload.
- GameState: 이닝/초말, 현재 공격 타석 완료 수, 스트라이크·아웃 수, 라이브/데드, 팀별 잔루, 팀별 완료 이닝, 수비 배치, 판정된 타석.
- Assessment: 선수·평가자·시각, G/F/C/A/L/Q/M/J/B 부분 점수, 타격·주루 기능, 실측 metric/value/unit 배열(초기 UI 미노출).
- TeamworkObservation: 선수, 선택 경기 ID, 영역, 행동, 관찰자, 시각, 임시 1~5 점수.
- EvaluationPolicy: 버전, 각 결정의 TODO/confirmed 상태·값·근거, 고정 주루 40/60.
- Selection: 팀, 10개 포지션 배치, 정책 버전, 원본 리비전, draft/approved, 승인자·시각.
- Workspace: schemaVersion=1, revision, 위 엔티티 컬렉션.

저장 시 컬렉션별 중복 ID, 소속 참조, 경기 명단, 이벤트 순서, 포지션/선수 중복, 승인 메타데이터를 검증합니다. 백업에서 임의 코드를 실행하지 않습니다.

### 플레이의 원자성

타구 발생 시의 잔루를 스냅샷합니다. 타임 입력에서 타자와 모든 잔루 주자의 결과를 하나의 이벤트로 확정합니다. 진루의 자동 추정은 하지 않습니다.

- 한 베이스 두 주자, 누락/중복 결과, 다른 팀 선수, 잘못된 점수·아웃 종류를 거부합니다.
- 마지막 타자 1루 포스아웃이면 바로 이전 스냅샷으로 잔루를 돌리고 그 타격의 모든 진루·득점은 통계에서 제거합니다. 타자 아웃·타석 및 실제 수비 관찰은 보존합니다.
- 출전 타순 슬롯 수만큼 타석을 완료하면 교대합니다. 3아웃 제한은 없습니다.
- 교대 시 상대 팀의 잔루 상태를 꺼내 사용하며 현재 팀의 잔루는 유지합니다.
- 악송구는 심판이 판정한 시점의 대상과 위치를 입력받아 1개 이상의 안전진루를 검증합니다. 공의 궤적·포스 관계·판정 타이밍을 자동 추정하지 않습니다.
- 추가 진루 후 아웃 등 복잡한 안전진루권 시퀀스는 초기 단일 최종 결과 모델로 완전히 표현하지 못할 수 있습니다. 후속 라이브 액션 모델 TODO입니다.

### 승패와 선발 통계

현재 점수 = 모든 확정 타석의 득점 합계.
승패 점수 = inning ≤ min(선공 완료 공격 이닝, 후공 완료 공격 이닝)의 득점 합계.
완료 이닝 0개면 판정 없음. 동점은 무승부. 설정 이닝이 양 팀 끝나면 종료, 콜드게임 없음.

전체 기록 통계는 모든 유효 이벤트를 보존합니다. 선발용 통계만 TODO-E06 정책의 영향을 받습니다. 두 개념을 혼용하지 않습니다.

## 6. 통계 정의와 한계

- PA: 확정 타석(삼진 포함), AB: PA에서 정책상 희생플라이 제외 여부 적용.
- H/TB: 1·2·3루타·홈런 결과를 기준으로 집계. 안타 후 추가 진루와 안타 종류는 별도.
- AVG=H/AB, AB=0이면 null. 관측 없음을 0점으로 표현하지 않습니다.
- 득점은 실제로 홈에 도달한 선수 ID에 귀속, 임시주자에게도 귀속.
- 수비: 입력된 관찰 성공/시도 횟수와 9개 유형별 빈도. 전통 야구 수비율의 PO/A/E와 동일하지 않습니다.
- 주루: 기록된 진루/태그업/오버런/위반 빈도와 주루 아웃. 전체 실전 능력 점수의 환산식은 TODO입니다.
- 스카우팅은 선수별 전체 경기의 방향·질·유형 빈도를 합산합니다.
- CSV는 통계 범위, 정책 버전, 미확정 여부를 포함하고 수식으로 해석될 수 있는 셀 선두를 이스케이프합니다.

## 7. 평가와 추천

포지션 적합도 = Σ(능력 점수 × 확정 가중치 / 100). 해당 포지션 가중치가 0인 능력을 제외하고 하나라도 결측이면 미산출(null)입니다.

10개 포지션 비트마스크 동적 계획법으로 전역 최대 합계 배치를 계산합니다. 시간 O(N × 10 × 2^10), 선수와 포지션 중복 없음. 충분한 입력이 없으면 추천 실패를 설명합니다. 동일 점수에서는 입력 순서가 결정성을 제공합니다. 적합도는 우선 소수 둘째 자리까지 계산합니다.

주루 blend(skill,game,{40,60})는 확정 비율. 타격/수비 mix와 composite는 초안 여부를 반환합니다. 부족한 실전 환산 기준을 만들어 점수를 채우지 않습니다. 현재 UI의 감독 승인은 시범 포지션 배치에 한정하고, 최종 종합 선발은 보류합니다.

## 8. 저장·백업·동기화 설계

현재: LocalWorkspaceRepository에 저장. 메모리에서 유효성 검증 후 저장 성공 때만 React 상태 갱신. 오류/용량 초과/손상 데이터는 가시적인 알림. 손상된 기존 데이터를 샘플로 덮어쓰지 않음.

- JSON envelope: format=tb-manager-backup, version=1, exportedAt, workspace.
- 복원 전 크기(10MB), 스키마, 모든 경기의 재생을 검증.
- 미리보기 후 사용자가 복원하면 현재 데이터 백업을 다운로드한 뒤 교체.
- revision으로 오래된 탭의 순차적 쓰기를 거부하고 storage 이벤트로 경고.
- localStorage read-check-write는 원자적이지 않음. 실제 동시 기록은 지원하지 않음.

목표:

1. IndexedDB의 단일 트랜잭션으로 이벤트와 outbox 기록.
2. 서버: gameId+eventId 고유키, expected server revision CAS, 경기별 기록자 lease.
3. UUID로 재전송 멱등성 보장, 서버 정렬 sequence 사용, 기기 시계로 정렬하지 않음.
4. 온라인 복귀 때 push/pull(cursor). 충돌은 명시적 재검토, 자동 last-write-wins 금지.
5. 교사 인증, 학급별 ACL, 감독 승인 권한, 전송 TLS, 서버 백업과 보존기간 정책.
6. schema/rules/policy 버전 마이그레이션과 재생 호환성을 별도 테스트.

공개 GitHub Pages는 정적 앱 호스팅만 담당합니다. 서버 동기화가 구현되었다고 표시하지 않습니다. 실제 학교 운영 전 접근 권한·기기 관리·백업·현장 검증이 필요합니다.
