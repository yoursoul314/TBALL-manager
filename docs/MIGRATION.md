# v1 → v2 데이터 보존 계획과 구현 계약

- RULE01~08 및 TYPE1 v2.0 설정 파일은 변경하지 않는다.
- v1 저장 키 `tb-manager.workspace.v1`을 삭제/덮어쓰지 않는다. v2는 `tb-manager.workspace.v2`에 저장한다.
- 최초 로드: JSON 파싱 → v1 스키마 검증 → 새 모델 변환 → 참조 및 전체 경기 재생 검증 → v2 저장. 검증/용량 오류 시 쓰기를 중단하고 원본 복구 다운로드를 제공한다.
- v2의 `legacySource`에 v1 원문을 그대로 보관한다. v1 이벤트 ID, 순서, 시각, payload 및 기존 팀워크 관찰은 변경하지 않는다. 원문에는 알 수 없는 확장 필드도 보존된다.
- v2 원문과 보존된 v1 키가 서로 다른 경우, 구버전 탭의 후속 쓰기일 수 있으므로 저장을 막고 두 원문을 다운로드하도록 안내한다. 복원으로 v1 출처가 달라지는 경우 현재 브라우저 v1 키를 별도 보존해 충돌 검사 기준으로 삼는다.
- 기존 타구 방향과 quality(타구 유형)는 유지한다. 거리·강도·타점·실책 판정은 추측해서 채우지 않는다. 누락 항목은 미기록이다.
- 모든 v1 팀워크 항목(책임감·존중 포함)은 `legacyTeamwork`로 이동하여 원래 분류·점수·관찰자를 보존한다. 새 기회/수행 결과와 합산하거나 자동 환산하지 않는다.
- 백업 v1과 v2를 모두 읽는다. 새 백업은 v2이며 legacySource/legacyTeamwork와 원본·수정 이벤트 전체를 포함한다. v2를 v1로 역변환하지 않는다. 구버전 앱에서 v2 백업을 열 수 없다는 점을 UI에 표시한다.
- 과거 플레이 수정은 REVISE_PLAY 이벤트(대상 원본 ID, 교체할 payload, 사유, 작성자, 시각)를 추가한다. 원본 배열은 불변이다. 전체 재생으로 후속 주자·타순 충돌을 검사하여 충돌 시 수정 저장을 거절한다.
- 기존 중복 타격 등 규칙과 모순되는 데이터는 자동 삭제/점수 보정하지 않는다. 원문을 보존하며 복구 오류로 알린다. 복구 도구/여러 플레이 일괄 정정은 TODO.
- 외부 파일 백업을 별도로 보관해야 브라우저 데이터 삭제에도 복구 가능하다. localStorage의 교차 탭 원자성, IndexedDB 트랜잭션, 서버 인증/권한/암호화/동기화는 TODO.

## 릴리스 검증

마이그레이션 반복 실행, 백업 v1/v2 왕복, 알 수 없는 버전, 잘못된 참조, 용량 초과, 구버전 탭 변경, 수정 후 전체 재생을 자동 테스트한다. 실제 학생 데이터는 테스트/저장소/배포 샘플에 사용하지 않는다.

## v3 날짜별 타격 평가 이전 계획 및 구현

- 읽기/쓰기의 현재 키는 `tb-manager.workspace.v3`이다. 기존 v1/v2 키를 삭제하거나 덮어쓰지 않는다.
- v3가 없으면 v2 우선, 없으면 v1을 읽고 기존 스키마/선수 참조/전체 경기 재생을 검증한 후 이전한다. v2의 v1 기준본 충돌도 먼저 검사한다.
- v1은 기존 legacySource.raw, v2는 migrationSource.raw에 입력 원문을 보관한다. 원문에는 알려지지 않은 확장 필드도 포함된다. 기존 Assessment.battingSkill, 경기 이벤트, 책임감·존중 기록은 변환하지 않는다. 새 세션/회차/감사 배열은 빈 배열이며 가상의 평가 횟수를 만들지 않는다.
- v3 전체 검증 후 한 번의 setItem으로 새 키를 쓴다. 용량 부족/검증 실패 시 이전 키는 그대로 남으며 성공을 표시하지 않는다. 복구 파일에는 v1/v2/v3 원문이 각각 들어간다.
- v3 저장 시 v1/v2 원문 기준본을 기록한다. 구버전 탭이 이를 바꾸면 쓰기를 중지하고 복구를 안내한다. 기존 리비전 검증과 storage 이벤트 감지도 세 버전 모두 적용한다. 동시 쓰기 원자적 잠금은 계속 TODO다.
- JSON 입력은 버전1/2/3, 출력은 버전3이다. 버전과 내부 스키마가 달라지거나 중복 회차, 잘못된 점수/날짜/참조, 끊어진 감사 이력, 최종 행과 다른 이력이 있으면 복원하지 않는다. 현재 데이터를 먼저 백업하는 기존 복원 UI를 유지한다.
- v3는 구버전 앱에서 열 수 없다. 배포 롤백 시 v1/v2 보존본은 남지만 v3 이후 신규 평가가 포함되지 않으므로 v3 JSON을 별도 보관하고 최신 버전에서 복원한다. 구버전 저장본을 다시 쓰거나 현재 v3를 강제로 지우는 자동 다운그레이드는 제공하지 않는다.
- 원문·이력을 중복 보관하므로 localStorage 용량을 더 사용한다. 기존 10MB JSON 입력 제한은 유지한다. IndexedDB/서버 저장, 인증·접근 권한, 암호화 백업과 자동 병합은 TODO다.

## v4 간편 기록 확장 (2026-10-20)

1. 작업 시작 시 기존 구조와 98개 테스트를 확인했다. 기존 v1/v2/v3 키를 남긴 채 `tb-manager.workspace.v4`를 신규 생성하는 계획을 우선 수립했다.
2. v4가 없으면 v3→v2→v1 순으로 선택한다. 이전 키 사이의 기준본 변경, JSON 스키마, 선수 참조, 경기 재생과 감사 이력 연결을 먼저 검증한다. 성공한 경우에만 v4를 한 번의 setItem으로 기록한다. 용량/검증 오류 시 이전 키는 그대로 보존된다.
3. v3 전체 원문은 `migrationSource: {schemaVersion:3, raw}`로 보존한다. 이전 원문의 기존 migrationSource/legacySource도 이 문자열 안에 유지된다. v3 세션·회차·before/after 감사 스냅샷을 변경하지 않는다. 기존 Assessment.battingSkill, 선수, 경기 이벤트, 팀워크 및 추천 기록은 유지한다.
4. 신규 회차에만 `direction: left|center|right|null`을 추가한다. `directionZone`은 거리까지 관찰했을 때만 설정한다. v3 회차의 direction 필드 부재는 그대로 두고 조회 시 기존 directionZone의 실제 방향을 사용한다. 거리를 추정하지 않으며 9구역과 방향이 불일치하면 거절한다.
5. 신규 경기 이벤트 버전은3이며 direction/quality와 수비 관찰 success를 nullable로 확장했다. 수비 difficulty는 routine/challenging/difficult/null의 선택 관찰이다. 기존 이벤트1/2도 계속 재생한다. v4 검증은 schemaCommon, 이전 v2/v3의 엄격 검증은 변경하지 않은 schemaV2를 사용한다. 판정 규칙과 포지션 가중치는 변경하지 않았다.
6. v4에는 v1/v2/v3 기준 원문을 함께 기록하여 구버전 탭 변경을 탐지한다. 복구 스냅샷은 네 키의 원문을 모두 담는다. 현재 리비전 검사와 storage 이벤트 탐지도 유지한다. 동시 쓰기의 원자적 잠금은 제공하지 않는다.
7. JSON 읽기1/2/3/4, 쓰기4. v4 이후 기록을 구버전으로 자동 다운그레이드하지 않는다. 배포 롤백 전 v4 JSON을 보관하고 최신 앱에서 복원해야 신규 기록을 잃지 않는다. 기존 복원 화면은 현재 데이터 백업 후 검증된 파일만 적용한다.
8. 원문 보존으로 저장 용량이 추가로 필요하다. 10MB JSON 입력 제한, localStorage 용량 제한은 유지한다. 서버 인증, 접근 권한, IndexedDB 트랜잭션 및 멀티기기 동기화는 TODO다.

## v0.5.1 사진 저장 호환성 (2026-10-26)

Workspace schemaVersion 5, localStorage 키, 경기 이벤트·기능평가 원본 및 JSON 백업 계약은 그대로 유지한다. 사진만 IndexedDB의 동일한 photos 저장소에서 읽기 호환을 확장한다.

- 기존 {playerId, blob, updatedAt} 행은 변경 없이 읽는다. 전체 사진을 일괄 변환하거나 삭제하지 않는다.
- 신규/교체 사진은 {playerId, bytes: ArrayBuffer, mimeType, updatedAt, formatVersion: 2}로 보관한다. WebKit에서 Blob 쓰기가 실패한 재현 사례를 해결한다.
- Blob→ArrayBuffer 변환은 트랜잭션을 열기 전에 완료한다. 쓰기 중 예외는 트랜잭션 전체를 중단한다. 읽기는 기존 PhotoRecord Blob 인터페이스로 복원하므로 사진 표시 및 암호화 백업 형식은 바뀌지 않는다.
- 선수 저장 실패 시 이전 사진을 복구한다. 사진 변환/저장 실패 시 기존 선수 정보를 변경하지 않는다. 삭제는 선수 저장 시에만 반영한다.
- 일반 JSON 백업은 이전과 같이 사진을 제외하며, 암호화 백업으로 사진을 함께 보관/복원할 수 있다. 이전 앱 버전은 새 사진 행을 읽지 못하므로 앱을 구버전으로 되돌릴 때는 현재 버전에서 암호화 백업을 먼저 보관한다.
- 시험은 별도 비영구 브라우저 컨텍스트의 가상 학생·도형 사진으로 수행한다. 실제 사용 중인 브라우저의 저장소는 읽거나 변경하지 않는다.

## v0.6 경기 목록·휴지통 — schema6

- v1~v5 JSON 백업을 계속 복원한다. 새 저장키는 tb-manager.workspace.v6이며 기존 v1~v5 키는 삭제하지 않는다.
- v5의 선수·사진 ID·엔트리·경기 이벤트·평가·수정 이력을 그대로 보존한다. 기존 경기는 삭제 상태를 추정하지 않고 활성 목록에 표시한다. 사진 IndexedDB 형식은 v0.5.1 그대로이다.
- Game.archivedAt(삭제 시각/null)과 archiveHistory(archive/restore,시각)를 추가한다. 삭제/복원은 경기 메타데이터만 변경하며 원본 이벤트를 지우지 않는다. 기본 목록·대시보드·경기 통계·프로필의 누적 경기 집계에서 휴지통 경기를 제외한다.
- 이전은 검증 후 새 키에 원자적으로 쓴다. 저장 실패 시 기존 키를 유지한다. 구버전 탭이 기존 키를 수정하면 기준값 비교로 추가 저장을 차단하고 양쪽 복구 파일을 제공한다.
- 경기 진행 중에는 삭제와 목록 이동을 차단한다. 마지막 경기를 삭제한 경우 빈 목록/빈 통계와 새 경기·휴지통 복원을 제공한다. 영구 삭제는 제공하지 않는다.

- Team에도 archivedAt/archiveHistory를 추가한다. 삭제는 운영 팀/새 경기 선택에서 제외하는 논리적 삭제이며 소속 선수·사진·평가·경기는 보존한다. 당시 Game.entry 팀 스냅샷도 변경하지 않는다. 선수 이동과 팀 복원이 가능하며 플레이 진행 중인 팀은 삭제하지 못한다.
- 기존 날짜별 평가 데이터 구조와 평균 계산은 변경하지 않는다. 상세 모드 전체 화면은 같은 회차 초안을 편집하며 모드를 닫아도 입력을 유지한다.
