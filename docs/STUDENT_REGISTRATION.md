# 학생 온라인 등록 · BETA 0.15.0

학생이 초대 링크로 신청하고 담당 교사가 승인하여 기존 선수 명단에 추가합니다. GitHub Pages는 화면을 제공하고 Supabase는 교사 인증과 신청 DB를 담당합니다. 개인 PC를 서버로 계속 켜 둘 필요가 없습니다.

## 사용 흐름

- 선수 & 팀 → 학생 온라인 등록 → 교사 로그인 → 새 접수 → 초대 링크 복사 → 학생에게 공유.
- 학생 전용 `?register=1#invite=…`: 이름·학년·반·번호, 선택적 1·2지망. 팀·등번호는 감독이 나중에 편성합니다. 사진·전화번호·주소·생년월일은 수집하지 않습니다.
- 학생은 계정을 만들지 않고 신청만 합니다. 다른 학생의 명단·점수 조회와 승인 API는 차단합니다. 초대 링크는 신원 증명이 아니므로 교사가 본인을 확인합니다.
- 교사 신청함 새로고침 → 승인·선수 추가. 반려 후 다시 승인할 수 있습니다. 동일 학년·반·번호는 직접 확인해 기존 ID에 연결하며 원래 선수 정보를 덮어쓰지 않습니다.
- 승인 후 기기 저장 실패 시 서버 승인은 남습니다. 같은 신청을 재반영하여 복구합니다. 다른 기기의 기존 학생과 충돌하면 원래 기기의 JSON 백업을 먼저 복원합니다.
- 링크 재발급 시 이전 링크는 만료됩니다. 접수 마감은 기존 신청을 지우지 않습니다.

## 데이터 보존·이전

1. 기존 schema14·저장 키·JSON 1~14 호환 경로를 유지합니다. 별도 서버 테이블만 추가하며 기존 자료를 자동 업로드하지 않습니다.
2. 승인 시 기존 Player 필드만 추가합니다. 신규 `reg-신청UUID` ID가 고정되어 재시도해도 중복되지 않습니다. 기존 선수 연결은 원래 ID 그대로입니다.
3. 기존 선수·경기·평가·사진은 유지됩니다. 선수는 기존 JSON 백업에 포함되지만 서버 신청함·로그인 토큰은 포함되지 않습니다. 기기 반영 전후 JSON 백업을 권장합니다.
4. 신청은 접수일+보관 일수(1~90일)에 만료됩니다. 조회에서 제외하고 일일 Cron으로 실제 삭제합니다. 승인 후 로컬에 반영한 선수는 이 정리로 삭제되지 않으며 학교 방침에 따라 별도 관리합니다.
5. 미연결 서버에서는 기능을 비활성화합니다. `?preview=1`은 실제 등록 서버에 연결하지 않습니다. 경기·평가 전체 동기화 기능은 이번 범위가 아닙니다.

## Supabase 개설·연결

실제 프로젝트·교사 계정·설정이 준비되어야 학생 접수가 작동합니다. 비밀번호·DB 비밀번호·service_role 키는 채팅이나 GitHub에 올리지 마세요.

1. Supabase 프로젝트를 만들고 학교가 허용하는 저장 위치·요금제를 확인합니다. 무료 서비스의 유휴 정지·백업·운영 조건은 개설 시 최신 안내를 확인합니다.
2. SQL Editor/연결 도구로 `supabase/migrations/202611050001_student_registration.sql`을 한 번 실행합니다. 비공개 스키마의 테이블은 RLS를 켜고 직접 접근을 금지하며 필요한 RPC만 허용합니다. 비공개 스키마를 Data API 노출 목록에 추가하지 않습니다.
3. Authentication의 공개 회원가입을 끄고 교사 계정만 관리자 절차로 생성합니다. 교사가 비밀번호를 직접 설정합니다. 앱에는 회원가입 기능이 없습니다.
4. 교사의 Auth user UUID를 확인한 뒤 SQL Editor에서 허용 명단에 추가합니다.

   ```sql
   insert into tb_registration_private.teachers(user_id)
   values ('실제-교사-Auth-UUID');
   ```

5. Cron 기능을 활성화하고 `supabase/retention-job.sql`을 실행합니다. UTC 18:15(한국 03:15)에 만료 신청·관련 감사 기록을 삭제합니다. 실행 기록을 확인하세요. 교사 계정을 삭제하면 그 교사의 접수·신청도 함께 삭제되므로 필요 자료를 먼저 확인합니다.
6. GitHub 저장소 Settings → Secrets and variables → Actions → Variables에 다음 두 **공개 설정**을 입력합니다.

   | 변수 | 값 |
   | --- | --- |
   | REGISTRATION_SUPABASE_URL | https://프로젝트ID.supabase.co |
   | REGISTRATION_SUPABASE_PUBLISHABLE_KEY | sb_publishable_로 시작하는 공개 키 |

   service_role·sb_secret_·DB 비밀번호는 사용하지 않습니다. Vite가 빌드 전에 잘못된 키 종류를 차단합니다. 두 변수가 없으면 기능이 비활성화됩니다. 로컬 개발은 `.env.example`을 참고한 `.env.local`을 사용합니다.
7. Deploy GitHub Pages를 다시 실행한 뒤 교사 로그인과 미등록 계정의 접근 거절을 확인합니다.
8. 가상 학생으로 링크 → 신청 → 승인 → 명단 추가 → 새로고침 → 중복 재반영 차단까지 검증하고 실제 학생 접수를 시작합니다. 다른 브라우저에서 신청 목록 접근 불가도 확인합니다.

## 권한·개인정보

- 교사는 수집 목적·문의처·승인 후 보관 기준을 학교 방침에 맞게 입력합니다. 학생에게 그대로 표시됩니다. 학교의 필요한 처리 근거·동의 절차는 별도로 확인하며 안내 확인 체크가 법정 동의를 대신하지 않습니다.
- 교사 세션은 메모리만 사용합니다. 로그아웃·새로고침 후 다시 로그인합니다. 학생 입력 내용은 localStorage/sessionStorage에 쓰지 않으며 재전송용 무작위 UUID만 남습니다.
- 초대 원문은 URL fragment에만 넣고 DB에는 SHA-256 해시만 저장합니다. 외부 QR·분석 서비스에 링크·학생 자료를 보내지 않습니다.
- 접수 정원 최대 500명, 접수당 분당 60건, DB 행 잠금·중복 제약을 적용합니다. 링크가 유출되면 마감/재발급합니다. 공개 대규모 모집·CAPTCHA·개별 IP 제한·학생 신원 인증은 추가 범위입니다.
- 승인·반려·마감·링크 변경 감사 이력을 보존하고 보관 기한이 지난 신청의 관련 이력도 정리합니다.

## 검증 범위와 파일

실제 PostgreSQL 엔진(PGlite)에 마이그레이션을 적용하여 역할별 접근·중복·재시도·승인·반려·만료·정원을 테스트합니다. Auth user와 auth.uid는 테스트용 구현이므로 실제 Supabase Auth/PostgREST/Cron·네트워크 검증을 대신하지 않습니다.

UI 자동 테스트는 서버 어댑터를 대체해 신청·실패 시 입력 유지·저장 실패 재시도·기존 선수 보존·백업·학생 화면의 교사 저장소 미접근을 확인합니다. 실제 iPad/스마트폰 화면·클라우드 연결은 별도 검증이 필요합니다. QR 생성, 사진 신청, 학생 자체 수정·로그인, 같은 접수의 여러 교사 공동 관리는 미구현입니다.

주요 파일: src/registration/*, src/Root.tsx, src/main.tsx, src/components/Players.tsx, src/App.tsx, supabase/*, .env.example, vite.config.ts, .github/workflows/pages.yml. RULE01~08·TYPE1 v2.0·평가 계산은 변경하지 않습니다.
